# Auditoría de seguridad y funcionalidad — CareLink v3.0

**Fecha:** 2026-08-06
**Alcance:** Sub-fase 8 del Milestone 1 (SRS §16.2). Todo el repositorio y la
aplicación corriendo contra `docker compose up`.
**Método:** revisión de código dirigida + herramientas (semgrep, sqlmap) + verificación
en vivo por HTTP + navegador real.

> **Nota de encuadre.** Esta es una implementación de referencia que corre únicamente
> con datos sintéticos y no se despliega a ningún entorno público (ADR-009, ADR-015,
> SRS §1.6). Los hallazgos se clasifican por lo que significarían en un sistema que sí
> manejara PHI real, porque es el estándar contra el que este artefacto quiere ser
> juzgado — no por su impacto en un entorno de demostración, donde sería cero.

El hallazgo crítico —un secreto criptográfico con valor por defecto escrito en el
repositorio— es la clase de defecto que este proyecto ya había eliminado una vez
(ADR-010) y que reapareció en otro archivo con otro nombre, **sin que ningún gate lo
detectara**. Eso, más que el defecto en sí, es la conclusión principal de la auditoría:
los gates que buscan un literal específico solo detectan ese literal.

## 2. Hallazgos

### H-01 · CRÍTICO · Secreto HMAC con valor por defecto público — CORREGIDO

**Dónde:** `TokenHasher.java:9` (antes de la corrección).

```java
private static final String secret =
    System.getenv().getOrDefault("REFRESH_TOKEN_HMAC_SECRET", "dev-refresh-secret");
```

**Qué significa.** `TokenHasher` calcula el HMAC-SHA256 con el que se guardan los
refresh tokens: la tabla `sessions` no almacena el token sino su hash, justamente para
que leer esa tabla no alcance para robar una sesión. Con este default, una instancia sin
la variable de entorno configurada arrancaba **normalmente** y hasheaba todos los tokens
con un secreto que está escrito en el repositorio. Cualquiera con acceso al código podía
calcular el hash de un token dado y —con lectura sobre `sessions`— reconocer sesiones o
fabricar el hash de un token elegido. El control de "guardamos hasheado" seguía
existiendo en apariencia y no protegía nada.

**Por qué ningún gate lo detectó.** El gate de AC-04 en `ci.yml` busca las cadenas
literales `HS256` y `dev-secret`. La cadena de este defecto es `dev-refresh-secret`, que
**no contiene** `dev-secret` como substring. El gate estaba correcto para lo que se
escribió y ciego para lo que apareció después. Gitleaks tampoco lo marca: es un literal
en código fuente con forma de identificador, no un patrón de secreto.

**Corrección.**
- `TokenHasher` ahora **falla** si el secreto no está configurado o tiene menos de 16
  caracteres. Mismo criterio ya aplicado a `CLINIC_ENCRYPTION_KEY` (AC-09): sin secreto,
  la aplicación no arranca. Un default permisivo convierte un control de seguridad en un
  adorno, y en uno que además parece estar puesto.
- `RefreshSecretGuard` (`@PostConstruct`) adelanta esa validación al **arranque**. Sin
  él, la validación recién dispararía al cargar la clase — es decir, en el primer login —
  y una instancia mal configurada respondería `/actuator/health` con `UP`, pasaría
  cualquier smoke test que no haga login, y fallaría con el primer usuario real.
- Gate nuevo en CI que busca el **patrón estructural** (`getOrDefault` sobre una variable
  cuyo nombre contiene SECRET/KEY/PASSWORD/TOKEN/CREDENTIAL) en vez de un literal.
  Verificado en las dos direcciones: en verde sobre el código corregido, en rojo al
  reintroducir el defecto a propósito.
- `SecretConfigurationGuardTest` cubre lo mismo por comportamiento, no por texto.
  También verificado rompiéndolo.

### H-02 · MEDIO · La regla semgrep de SQL no cubría la forma que el código usa — CORREGIDO

**Dónde:** `.semgrep/no-string-sql.yaml`.

La regla existente era exactamente:

```yaml
pattern: String sql = "..." + $X;
```

**Qué significa.** Ese patrón cubre una forma de escribir SQL que **este codebase no
usa**: los nueve repositorios con SQL dinámico arman la consulta con `StringBuilder` o la
pasan directamente a `jdbcTemplate.query(...)`. La regla llevaba varias sub-fases en
verde sobre código que nunca había mirado. No es un falso negativo sobre una
vulnerabilidad concreta —no había ninguna, ver §3— sino algo peor de sostener en el
tiempo: una señal de cobertura que no cubría.

Además, el `todo.md` de esta sub-fase pedía explícitamente cubrir **JPQL**, y no existía
ninguna regla para eso.

**Corrección.** Tres reglas: la original, una para concatenación dentro de llamadas JDBC,
y una para JPQL/consultas nativas. Dos detalles que importan:

1. Los patrones usan `$A + $B` y no `"..." + $X`, porque en Java `"x" + v + "y"` se
   parsea como `(("x" + v) + "y")` — un patrón anclado al literal de la izquierda **no
   matchea** la inyección clásica. Esto se descubrió escribiendo un archivo
   deliberadamente vulnerable y comprobando que la primera versión de la regla no lo
   detectaba.
2. Las excepciones (`schema`, `sql + "literal"`) son por **nombre de identificador**, a
   propósito: se apoyan en que esos dos están auditados en este repositorio, no en una
   heurística general de "concatenar literales es seguro" — que sería falsa, porque la
   inyección clásica `"... '" + userInput + "'"` también termina en un literal.

Verificación: 3 hallazgos sobre el archivo vulnerable, 0 sobre el código real.

### H-03 · MEDIO · Healthcheck del frontend siempre en rojo — CORREGIDO

**Dónde:** `docker-compose.yml`, servicio `frontend`.

El healthcheck usaba `wget http://localhost/`. Dentro del contenedor, `localhost`
resuelve primero a `::1`, y nginx con `listen 80` solo bindea IPv4 — el healthcheck daba
`connection refused` y marcaba `unhealthy` un servicio que respondía perfectamente por su
puerto publicado.

**Qué significa.** Un healthcheck permanentemente en rojo deja de ser una señal, igual
que uno permanentemente en verde: en ambos casos, el día que el servicio se caiga de
verdad nadie lo va a notar por ahí. Es el mismo modo de falla que el `|| true` que este
proyecto ya sacó de CI una vez.

**Corrección:** `http://127.0.0.1/`. Los cuatro contenedores quedan `healthy`.

### H-04 · INFORMATIVO · Filtro por edad del Motor de Conocimiento no soportado — DOCUMENTADO

FR-CLN-06 pide filtrar por rango etario. No está soportado y el endpoint devuelve `501`
con una explicación. `date_of_birth` está cifrada (AC-09) y un ciphertext no admite
comparación por rango en SQL.

Se registra como hallazgo informativo y no como defecto porque **falla ruidosamente**:
ignorar el filtro en silencio devolvería un conjunto **más amplio** que el pedido,
presentándolo como el pedido — un resultado clínicamente engañoso, sobre más pacientes de
los que el usuario creyó estar consultando. Las tres salidas posibles (columna derivada
de banda etaria, cifrado que preserve orden, o descifrar y filtrar en memoria) tienen
cada una un costo de privacidad que merece su propio análisis, no una decisión tomada de
paso.

### H-05 · INFORMATIVO · `sqlmap` no pudo evaluar `/api/v1/auth/login` — MITIGADO POR OTRO CONTROL

El escaneo contra el endpoint de login quedó **no concluyente**: sqlmap reportó
`target appears to be rate-limiting requests; sqlmap is backing off and throttling
accordingly` y el análisis time-based se volvió impracticablemente lento.

La causa es el rate limiter de FR-ID-03, o sea un control funcionando como se diseñó —
pero el resultado honesto es que ese endpoint **no tiene evidencia dinámica** de estar
libre de inyección. La evidencia que sí hay es estática y sólida: el login consulta vía
`UserJpaRepository.findByEmail(String)`, una query derivada que Spring Data genera
parametrizada, y el proyecto **no tiene un solo `@Query` escrito a mano** (verificado por
`grep`). No hay ninguna cadena SQL que concatenar en ese camino.

### H-06 · INFORMATIVO · Convención de nombre de variable en `JdbcPharmacyRepository` — CORREGIDO

Una variable local que contenía SQL se llamaba `check` en vez de `sql`, lo que la dejaba
fuera de la excepción auditada de la regla semgrep nueva y generaba dos hallazgos.

Se corrigió **el código**, alineándolo a la convención de los otros ocho repositorios, en
vez de ampliar la lista de excepciones de la regla. Una lista de excepciones que crece
con cada nombre nuevo deja de ser una excepción acotada y se vuelve un colador.

## 3. Superficie de inyección SQL — revisión de código

Se revisó **cada** concatenación de SQL del código de producción:

```
38 concatenaciones en consultas · 100% de la forma  "..." + schema + "..."
```

Sin excepciones: ningún valor de usuario se concatena en ninguna consulta. Lo único
interpolado es el nombre del schema del tenant, que **no puede** ir parametrizado (SQL no
admite un identificador como parámetro) y que los **nueve** repositorios con SQL dinámico
revalidan contra `TenantSlug.PATTERN` y comillan con `PostgresIdentifiers.quote` antes de
usar (AC-05). Verificado uno por uno:

| Repositorio | Revalida `PATTERN` | Comilla |
|---|---|---|
| `JdbcPatientRepository` | ✓ | ✓ |
| `JdbcClinicalEncounterRepository` | ✓ | ✓ |
| `JdbcAdmissionRepository` | ✓ | ✓ |
| `JdbcHealthDiaryRepository` | ✓ | ✓ |
| `JdbcKnowledgeEngineRepository` | ✓ | ✓ |
| `JdbcInterconsultationRepository` | ✓ | ✓ |
| `JdbcPrescriptionRepository` | ✓ | ✓ |
| `JdbcLabRepository` | ✓ | ✓ |
| `JdbcPharmacyRepository` | ✓ | ✓ |
| `JdbcAuditEntryAdapter` | ✓ | ✓ |

El Motor de Conocimiento merece mención aparte por ser el único con SQL **dinámico por
filtros opcionales** — el patrón que §8.4 marca como vector. Lo que se arma dinámicamente
es solo la presencia o ausencia de fragmentos `AND columna = ?` fijos escritos en el
archivo; todo valor viaja como parámetro posicional.

## 4. AC-11 — sqlmap

`sqlmap 1.10.8`, `--level=3 --risk=2 --dbms=postgresql`, contra la instancia de
`docker compose`. Se cubrió el vector de cabeceras que AC-11 exige explícitamente.

| Objetivo | Parámetros probados | Resultado |
|---|---|---|
| `GET /api/v1/patients/{id}` (autenticado) | URI, `User-Agent`, `Referer` | **No inyectable** |
| `GET /api/v1/knowledge/search` (autenticado) | `diagnosisCie10`, `nandaCode`, `sex`, `User-Agent`, `Referer` | **No inyectable** |
| `POST /api/v1/auth/login` (sin autenticar) | `email`, `password` (JSON) | **No concluyente** — ver H-05 |

El segundo objetivo es el importante: es el único endpoint con SQL dinámico construido a
partir de filtros que el cliente controla.

**Logs:** no se commitean los `.log` crudos de sqlmap — contienen tokens de sesión de la
corrida. Los comandos exactos están arriba y son reproducibles contra un `compose up`
limpio.

## 7. Conclusión

La postura de seguridad del sistema construido es sólida en lo estructural: el
aislamiento por tenant y por servicio no depende de comparaciones en runtime que puedan
tener un bug, sino de que el dato para pedir lo ajeno no exista en la forma de los
endpoints; la inmutabilidad de la historia clínica y el append-only del audit log están
en triggers de base que aplican a cualquier rol, no en lógica de aplicación; y el
k-anonimato se aplica dentro de la consulta, no filtrando en memoria lo que la base ya
devolvió.

El hallazgo crítico no contradice eso: es un recordatorio de que los controles fuertes
conviven con defectos ordinarios, y de que **un gate que busca un literal solo detecta
ese literal**. Los tres gates nuevos que salieron de esta auditoría se verificaron
rompiéndolos a propósito antes de darlos por buenos — que es la única forma de saber si
un gate existe o solo parece existir.

```bash
  services/*/src/main --include=*.java \
| grep -vE '(TTL|TIMEOUT|_DAYS|_SECONDS|_MS|_MAX|_MIN|LENGTH|COUNT|ENABLED|ALLOWLIST)'

# Credenciales versionadas (AC-03, AC-04)
git ls-files '*.db'; git ls-files | grep -E '^\.env$'
grep -rn "HS256\|dev-secret" services/

# SAST — debe dar 0 sobre services/ y 3 sobre un archivo deliberadamente vulnerable
semgrep --config .semgrep/ services/

# Suite completa (unitarios + integración contra PostgreSQL real, vía Failsafe)
cd services/identity-service && mvn clean verify

# sqlmap (requiere el stack levantado y un token válido)
sqlmap -u "http://localhost:8080/api/v1/knowledge/search?diagnosisCie10=J45.9" \
  --headers="Authorization: Bearer $TOKEN" --level=3 --risk=2 --batch --dbms=postgresql
```

## 9. Lo que esta auditoría NO cubrió

Declarado explícitamente para que nadie lea más cobertura de la que hay.

- **Historial de git.** `test_identity.db` (hashes Argon2id de prueba) sigue siendo
  recuperable de commits anteriores. Purgarlo exige reescribir historia, lo que invalida
  clones y forks existentes — decisión reservada al autor, abierta en `tasks/todo.md`
  desde la Sub-fase 0.
- **Escaneo dinámico completo de `/api/v1/auth/login`** — ver H-05. La evidencia ahí es
  por inspección de código, no por escaneo: es sólida, pero de otra naturaleza.
- **Pentesting de la SPA** (XSS almacenado, CSRF, clickjacking) más allá de las cabeceras
  que fija nginx y de la decisión de mantener el access token fuera de `localStorage`.
- **Análisis de dependencias con datos frescos.** El gate de OWASP dependency-check
  existe en CI (bloqueante en CVSS ≥ 9) pero no se ejecutó en esta pasada: necesita
  descargar la base de la NVD, no disponible en tiempo razonable en este entorno.
- **Carga y denegación de servicio.** El rate limiter es en memoria y por instancia: con
  más de una instancia el límite efectivo se multiplica. Documentado en el SRS, no medido.
- **Ejecución real del workflow en GitHub Actions.** Cada comando se verificó localmente,
  incluidos los gates nuevos rotos a propósito, pero el pipeline no corrió en la
  infraestructura de GitHub — no hay acceso a ella desde este entorno. No se marca como
  hecho lo que no se vio correr.
